# Shoot Clip — render exactly one clip

One task = one clip = one render. Never render another clip, another take of this clip (except the single retries of section 7 and the bundle fallback of section 8), or other shots. A task with `mode: bundle` shoots ONE multi-shot clip: follow section 8 instead of sections 2-6. A `continue` clip right after a bundle has the bundle's LAST member shot as its prior shot: its `prior_clip` is the bundle clip, measured and offset like any prior clip (section 3), so it continues from the bundle's last seconds. Never `create_task`. This skill is the authority for the `continue` mechanics (section 3), which `shoot-continuation` reuses.

## 1. Preflight

Task prompt fields:
- `mode: bundle` (field `bundle_brief`): section 8 only; its fields are listed there.
- Required: `scene`, `clip`, `clip_ref`, `workflow`, `shot`, `mode` (`continue` | `cut`), `movement`, `duration_seconds`, `picture_map`, `style`, the canonical output files (`.mp4` and `_prompt.txt`); `cut` also `start_frame`; `continue` also `prior_clip` (the KEY of clip M-1's output artifact, e.g. `scene2_clip3`), `seam_keyframe` (this shot's own storyboard frame: only the seam check's comparison image - NEVER an input of a continuation) and `seam_check`.
- Used when present: `action`, `camera`, `beat` (the scene-list beat of this shot, verbatim), `prior_shot_facts` (`continue`: the previous shot's Action / Wardrobe / State lines), `framing_change`, `negative_prompt`, `loras` (the shot's curated LoRAs), `shot_block` (the shot's full block: Blocking, Pose, Frame, Visible, Sex act, Sex position …), `frame_edits`. (`width` / `height` are ignored: a clip keeps its start frame's shape.)

`task_failed(reason)` (render nothing; deterministic causes only) when:
- a required field is missing (name it);
- `continue`: the `prior_clip` key does not resolve (`artifact_index`) to an artifact with an approved video file - resolve the key to `artifact://<artifactId>/<its .mp4>` HERE, at run time (`read_artifact`), and use that reference for every later step;
- `shoot_clip` is unavailable, or answers that the workspace has no workflow for this mode (reason: name it - "no image-to-video workflow - add one and ask again" / "no video-continuation workflow").

## 2. Workflow and pictures: the server's

`shoot_clip` is your ONE render tool for this clip. The server picks the workflow of the mode (`workflow:` of the brief: image-to-video for a `cut`, video-continuation for a `continue`) and fills EVERY mechanical port from the current clip plan: the start frame (`cut`: Picture 1), the identity and place reference pictures, the voice references, the duration and the LoRAs. The brief's `picture_map:` lists exactly what it binds - which `<Picture N>` is whom, in which look at the clip's start (`nude in this clip`, `wearing: ...`) - and which `<Audio N>` is whose voice. You choose none of it: NEVER pass an image port, a reference, a voice file, a duration or a LoRA, never call a `wf_*` tool for this clip, and never add, drop or reorder a picture. A `continue` binds no storyboard frame: `<Video 1>` (the prior clip) carries the framing. Its prior clip, `prior_clip_start_time` and pinned end frame are filled by the server from the seam decision `prepare_continuation` stored for this clip - you pass none of them, and `shoot_clip` refuses a continuation until that call has answered.

- Read `get_workflow_instructions` of the brief's `workflow:` once (prompt syntax, duration, frame constraints). State the workflow and mode in the summary.
- A `cut` is never faked through the continuation workflow and never rendered text-to-video.

## 3. Mode `continue` (authority for continuation mechanics)

A continuation starts from the prior clip's REAL last frame. The server checks that seam; you never measure, offset or compare it yourself.

- FIRST call `prepare_continuation({ clip_ref: <the brief's clip_ref> })` - once, before drafting the prompt (the answer is remembered; a retry returns the same). The server derives everything else (this shot's lines, its storyboard keyframe, the continuation workflow, the prior shot's camera) from the clip plan, and the prior clip is the video your task requires; add `prior_clip: artifact://<id>/<mp4>` only when the result asks for it. On an `error:` result call it again (up to twice in all); only after it FAILED TWICE may you shoot the clip as a CUT: `shoot_clip({ clip, prompt_id, as_cut: true })` - the server refuses `as_cut` before that and over any seam answer other than `cut`; it renders it from the shot's own start frame with the single-cut workflow - draft the prompt for that (this shot's own Action / Motion from its first frame) and begin the final reply with `Shot as a cut: seam check failed - <its error>.` Never `task_failed` for a failed seam step.
- `prior_clip_start_time`, the pinned `end_frame` and the prior clip's audio are filled in by `shoot_clip` from that answer: NEVER compute, pass or bind them yourself, never call a `wf_*` tool for this clip. The result's `end_frame` only reports what will be pinned (`{ port, source }` or `null`; `storyboard`: the shot's own frame, judged reachable from the real end; `derived-crop`: a crop of the real last frame for a push-in) - quote the source in the summary; the prompt's final beat of Motion arrives at the framing it shows.
- `outcome: as-planned`: write the prompt from the brief as planned (`prior_shot_facts` holds).
- `outcome: adjusted`: the prior clip's real end differs from the plan. Use the result's `brief` block: its `seam_state` is what the last frame of `<Video 1>` really shows - the shot's Motion starts FROM it and moves toward the shot's lines without a jump, a lunge or a cut. It REPLACES `prior_shot_facts`; never brief from the planned end state. Put the `brief` block in the prompt `context`.
- `outcome: cut` (reason `seam-incompatible`): the shot cannot continue from the prior clip's real end. `shoot_clip` then renders this clip as a CUT from the shot's own start frame with the single-cut workflow (no prior clip, no end frame): draft the prompt for THAT - this shot's own Action / Motion from its first frame, not the prior clip - and begin the final reply with `Shot as a cut: seam-incompatible - <the result's note>.` Keep the task's file name and outputs; never `task_failed`.
- The prompt continues `<Video 1>` in the same shot: same framing, subject and setup, the action carrying on, the `movement` continuing or holding. NO cut ("the target video cuts to …"), no new composition. Output is only the new segment; do not merge.
- `framing_change: yes` is valid only with a `movement` that can reach the new framing (`push in` / `pull out` for a change of shot size, `arc left|right` for a new side of the subject, `crane` / `pedestal` for a new camera height; a pan, tilt, truck, follow or handheld movement does not): write the shot's `movement` VERBATIM (canonical grammar `<move> <dir> [N°], from <frame> to <frame>`) as the only camera move - never invent a reframing; no storyboard frame is bound or added (the server binds none into a continuation: `<Video 1>` carries the framing); subjects, place, lighting, wardrobe stay those of `<Video 1>` (the look of each picture is the `picture_map:`'s).
- Test the `movement` against the change before choosing `continue`: a change of shot size needs a size move (`push in` / `pull out`), a new side of the subject an `arc`, a new camera height a `crane` / `pedestal`, several changes one move each - a pan does NOT turn a front view into a three-quarter one, a push-in does NOT turn eye level into low angle. The planner's rule R25 refuses such a pair at the storyboard write, so a brief that still carries one is planned wrong and is shot as a `cut` (below).
- `framing_change: yes` without such a movement (`hold`, none) was planned wrong. You cannot turn it into a cut yourself (`as_cut` is refused unless the seam step ordered a `cut` or failed twice): do not invent a reframing move - write the shot's `movement` verbatim, and begin the reply with `Plan mismatch: framing change without a camera move that can reach it.` so the plan is corrected. A new subject or insert is planned as a CUT by the server.
- **Declared limits (restructure, never render as written).** Read the workflow's `limits:` and `camera:` (from `workflow_index` / the manifest). A move outside `camera.reliable`, inside `camera.unreliable` or an arc above `max_arc_degrees` does not hold up a `continue` (you cannot cut it yourself: `as_cut` is refused) - replace it by a reliable move in the prompt and name that in the reply (`Replaced move: ...`). A beat that matches a limit class is RESTRUCTURED before the prompt is written: `medium-transition` (a body entering / leaving water, fire, smoke) - end this clip at take-off and shoot the rest as the next clip starting inside the new medium; `micro-motion` (fingertips, blinks) - a larger visible motion of the same action or a close insert of the thing; `late-interaction` (hand-off / contact after `max_start_seconds`) - move the interaction to the first seconds or split it across clips; `short-utterance` (fewer than `min_words`, default 3, spoken words) - lengthen the line to at least `min_words` words with the dialogue the beat already implies. Name each restructuring in the reply (`Restructured for <class>: ...`); never render the beat as written and hope.

## 4. LoRAs

The server passes the shot's curated LoRAs (brief `loras`, rank order) that fit the workflow's family; you pass none. Only their trigger words matter for the prompt: `lora_index()` once to read them for the writer's `context` (no realism / skin / anatomy / detail / style LoRA words: the keyframe and the workflow's baked-in LoRAs carry looks), and name the list in the summary.

## 5. Prepare the prompt

Follow "Prompt route" of `workflow-calling-conventions` (`load_skill` it).

- Normal: ONE `draft_prompt`; then ONE `review_prompt` (the completeness check below); one `enhance_prompt` only if it flags a gap. No per-step loops.
- **Completeness check (before the render).** `review_prompt` with the `prompt_id` the draft returned (never retype the prompt) and `review_instructions` = the `shot_block` + `beat` + `prior_shot_facts` VERBATIM, prefixed with the single line "Check that the prompt states every element of this shot (who, where, extent, pose, wardrobe and state changes, the action from start to end, camera move, dialogue, out-of-frame constraints) and contradicts none. List each missing or contradicted element." Do NOT write your own rubric, scoring criteria or "what a good clip looks like": the shot block IS the rubric. Severity "significant" -> `enhance_prompt` with `prompt_id` and the review text as `additional_context`, once.
- Re-run ("## Instructions for this run" in the kickoff): the instructions OVERRIDE the shot block wherever they conflict.
  - Drop contradicted lines (e.g. "no contact", "neutral expression") from `context`; pass the instructions VERBATIM as `instruction` (not only inside `context`).
  - Previous prompt available (old `_prompt.txt` or `render_info`): `enhance_prompt(original_prompt, instruction)` INSTEAD of `draft_prompt`, then the completeness check once on the writer result (draft or enhance, by its `prompt_id`) with the same `instruction`, `enhance_prompt` once more only on severity "significant" (max 2 enhances + 1 review). All before the one render.
- The clip's motion is a FROM -> TO delta, written into `context` as the action in progress (never as a frozen pose, never as a list of prohibitions):
  - `continue`: FROM = the end state of the prior clip (the `seam_state` of an `adjusted` seam - the real last frame -, else the planned `prior_shot_facts`: its Action / Wardrobe / State), TO = this shot's state (`shot_block` Action / Wardrobe / State). A Wardrobe or State change between the two (a garment removed, wet hair, a prop picked up) IS this clip's action: state it as happening during the clip, in the shot block's words.
  - `cut`: FROM = the start frame, TO = what the `beat` text says happens (verbatim). The shot's `Action:` is the state AT 0 s; the beat carries it forward.
  - Add no behaviour the shot block and beat do not state. The clip ENDS with the shot's last Motion beat: nothing of the next shot (its jump, dive, exit) goes into this clip's context or prompt.
- Always pass `workflow_name` (the brief's `workflow:`), `context`, `duration_seconds`, and `verbatim_phrases`: the shot's `Sex act:` / `Sex position:` values (only when `shot_block` has them; read only in a workspace with `contentPolicy.nudity: allowed`) and dialogue to keep. No `image_inputs`: the brief's `picture_map:` names the pictures (a seam `cut` outcome: the start frame is Picture 1 of the same map).
- `duration_seconds` = the brief's planned duration, passed to `draft_prompt` (the server sets the render's own duration port).
- `context`:
  - the brief's `picture_map:` block VERBATIM (every `<Picture N>` / `<Video 1>` / `<Audio N>` line with its look at the clip's start, and the `picture_notes:`). The writer's `subject_definitions` take each subject's LOOK only from these lines and the `shot_block` (`Wardrobe:` / `State:`) - never from the style line, the plot, a design's name or another shot; a picture labelled `face and identity only` gives identity, never its clothes;
  - the `shot_block` VERBATIM (Blocking, Pose, Frame, Visible, Sex act, Sex position stay as written);
  - the brief's `Visible anatomy (must show)` line VERBATIM when it has one (the genitals and join the act must display), with the shot's `State:` fluids (`shot_block`): the writer names them in plain anatomical words;
  - the brief's `Lighting (scene, keep)` line VERBATIM when it has one (the writer keeps the phrase);
  - the brief's `Expression (<name>): … (must show)` lines VERBATIM when it has them;
  - `beat` VERBATIM (the scene-list beat text: Action, Blocking, Camera move …), and for a `continue` the `seam_state` (`adjusted`) or `prior_shot_facts` (`as-planned`);
  - `movement` VERBATIM, canonical ids only - a legacy `zoom` / `dolly` / `track` / `orbit` is rewritten to `push in` / `pull out` / `truck` or `follow` / `arc` before it goes to the writer ("hold" = locked-off frame; no `movement` = the framing of `camera`, no camera move added);
  - `cut` with a start frame: describe only the motion from that frame;
  - `style` verbatim (a clip in another medium is a miss); the optional `setting` line is the era / place of the story - no prop, device, vehicle or garment of the clip may contradict it;
  - `frame_edits` restated as a constraint: never re-add an element an edit removed ("remove the car" = no car in the clip prompt);
  - `speakers` (only when the clip has dialogue): the clip's speakers in ONE fixed order - the order of their first appearance in the rows of `character_table.md`, among the clip's speakers only: `S1` is the first, `S2` the next, `S3` ... (never the order of the dialogue lines). One line each: `S# = <Subject n> = <character design key>`, then the character's `voice` attribute text VERBATIM (`read_artifact` of the character design, its `design.json` attributes; never paraphrase, shorten or invent a voice). The `<Audio N>` lines of the `picture_map:` say whose voice sample the server bound (the first two speakers that have one); every other speaker has the voice text only - never another character's file. Tell the writer the pairing with the map's audio numbers; a `continue`'s `<Video 1>` soundtrack is NEVER cited as anyone's voice when a voice reference is bound;
  - prohibitions (an `Out of frame:` line, a removed element, "no contact") are stated ONCE as constraints in `context` ("Constraint: nothing of X is visible") - never pasted as raw "do not" text into the drafted prompt, and never added to the prompt after the writer returned.
- Use `negative_prompt` when the workflow has a negative-prompt port; then also route the shot's `Out of frame:` things there (appended to it) instead of the prompt body. Without a negative port they stay in `context` as a constraint, and the writer states them as "Not in frame: no …".

## 6. Render

- Kickoff lists checks gating this clip: call `run_checks` BEFORE the render and fix every listed problem (a rejection after rendering wastes the render; "Checks that gate the task" in `workflow-calling-conventions`).
- ONE `shoot_clip({ clip, prompt_id })`: `clip` is the brief's `clip_ref:` value passed unchanged (`<storyboard key>#c<N>@<shotlist md5>`), `prompt_id` the writer's result id, never retyped text (the prompt-route guard refuses it); `seed` only on a retry (a `continue` needs no more: the prior clip, its start time and the end frame come from the stored seam decision). `draft` quality; the `.mp4` goes to the canonical path. No other render call.
- An `error:` result "call prepare_continuation first": do that, then shoot again. Any other `error:` result means the plan changed or has problems: call `clip_plan(storyboard)` again and read it - if the clip is gone, became a bundle or its `clip_ref` / brief changed, `task_failed` (deterministic) naming it so the coordinator re-plans; a plan with `PROBLEMS`: `task_failed` with them. Never retry the same call blindly.
- NEVER pass `width`, `height` or `is_portrait` on a clip: the clip keeps its start frame's aspect ratio (a contradicting value is refused). Size: "Render size" of `workflow-calling-conventions`.
- Error: read the failure result. `retryable: false` (infrastructure failure the server already retried, or `cancelled`) -> do NOT render again: quote the error in the final reply and end WITHOUT `task_failed` / `task_complete`. Otherwise (a wrong argument or output you can fix): fix, retry ONCE with the SAME tool; failing again -> quote the error and end the same way. The server enforces this: a task has a budget of 2 failed renders, and once it is used up every render call is refused with "render failures for this task are used up (2 of 2): report the problem and stop - do not render again" and the task ends as a declared failure - never try to render after that. A failed render never makes another workflow type acceptable (no text-to-video fallback).
- **Cut check (every `cut` and `continue` clip, right after a SUCCESSFUL render).** `check_clip_render({ clip_ref: <the rendered .mp4>, clip: <the brief's clip_ref> })`, once per render (the pinned end frame of a continuation is read from its stored seam decision; you pass none). `retry: true` (a hard cut inside the clip): render it ONCE more with `shoot_clip` (the SAME `prompt_id`, a NEW `seed`), route it to the same canonical path, check again. Still flagged (`retry: false`): accept it and put the result's `note` in the final reply - never a third render, never a different tool. A weak landing on the pinned end frame is only reported in the note, never a reason to retry. An `error:` result: skip the check and say so in the reply.
- Write the canonical `_prompt.txt` from the EXACT prompt the render got - the prompt `render_info` reports, which begins with the server's `Shot limits (authoritative ...)` block (the shot's last beat, camera and keep lines; `shoot_clip` / `shoot_bundle` put it in front of the writer's prompt for every shot with Motion beats - you never write, pass or remove it) (continue: plus a line `prior_clip_start_time: <the seam result's value>`); never reworded.

## 7. Pre-completion audit

- Call `render_info({ render_id })` with the returned `renderId` and compare with your call:
  - the media inputs are exactly the `picture_map:`'s (start frame + pictures + voices; a `continue` its prior clip, the `prior_clip_start_time` and the end frame of its seam decision, and no storyboard frame); anything else is a server fault: report it in the final reply, never patch it by rendering through another tool;
  - the prompt is yours behind the server's `Shot limits` block (a shot without Motion beats has none); the `continue` start offset and end frame are the seam decision's, never yours.
- The `.mp4` exists at exactly the canonical path and is a `shoot_clip` render (a path elsewhere breaks the artifact build: render again to the declared path).
- `get_video_info`: duration within ±0.6 s of `duration_seconds`; outside -> re-render ONCE (same prompt, new seed), keep the better; still off -> report the measured value rather than looping.
- `continue`: first frames fit the predecessor's last frames (same subject, place, lighting); a clear break -> one retry with a corrected prompt ("Check, retry once, suggest" in `workflow-calling-conventions`).
- The prompt file holds the rendered prompt; no other file written.
- `task_complete`: 1-3 lines — mode, measured duration, (continue) the start offset and the end frame source, the render check note when it flagged; no prompt / workflow restated ("Concise replies and task/artifact URIs" in `workflow-calling-conventions`).

## 8. Mode `bundle` (one multi-shot clip, several shots)

Task fields: `storyboard`, `bundle_brief` (its `bundle_ref:` line names the bundle), `duration_seconds`, `style`, `negative_prompt`, the canonical files. `task_failed` (deterministic) when `bundle_brief` has no `bundle_ref:` line or a canonical file is missing, or `shoot_bundle` is unavailable. The server owns everything mechanical: NEVER set guide frames, cut times, keyframes, reference order, identity references, LoRAs, voice references, ports or size, and never pass any of them; the plan already decided them.

1. **Prompt.** `load_skill` `prompt-writer-minimaxh3` (exactly this name - the MiniMax H3 prompt writer; if it is reported missing, take the `prompt-writer-*` name from the skill index, never invent one) via the "Prompt route" of `workflow-calling-conventions`: ONE `draft_prompt` with `workflow_name` = the multi-shot workflow (capability `multi-shot-clip`) copied VERBATIM from the task brief (`preferred_workflow`) or from your `wf_*` tool list - the name differs per workspace (e.g. `h3_multishot_clip_nsfw` in an NSFW workspace), so never derive, shorten or guess it from a name you remember; a "workflow … not found" error lists the valid names with `context` = the `bundle_brief` VERBATIM (every line: shot blocks with time windows, `picture_map:`, `continuity_constraints:`, `Audio:`), `style` verbatim, `duration_seconds`; no `image_inputs` (the brief's `picture_map:` names the pictures). Then ONE `review_prompt` as in section 5 with the brief as the instructions, adding: "every continuity_constraints line appears verbatim; each shot has its `[Shot k]` at its brief time". Fix a gap with one `enhance_prompt`. Do not invent, number or reorder pictures yourself.
2. **Render.** `run_checks` first if the kickoff lists checks. ONE `shoot_bundle({ bundle, prompt_id })`: `bundle` is the brief's `bundle_ref:` value passed unchanged (`<storyboard key>#<bundle id>@<shotlist md5>`; a bare `b1` is refused) and `prompt_id` is the writer's result id, never retyped text (the prompt-route guard refuses it); `seed` only on a retry. The `.mp4` goes to the canonical path. No other `wf_*` call. An `error:` result means the plan changed or has problems: call `clip_plan(storyboard)` again and read it - if the bundle is gone or its `bundle_ref` / brief changed, redo step 1 from the NEW brief (that is not a review failure); if the plan has `PROBLEMS`, `task_failed` with them. Never retry the same call blindly.
3. **Review per segment.** `get_video_info` (duration within ±0.6 s of `duration_seconds`). Then, per shot k of the brief, extract that shot's time window as ONE strip (`troubleshoot-production` step 2 recipe: `ffmpeg -y -nostdin -ss <start> -t <window> -i clip.mp4 -vf "fps=6/<window s>,scale=480:-1,tile=6x1" -frames:v 1 strip_k.png`, saved under your artifact folder) and compare it with that shot's block (`describe_image` on the strip with the shot block's who / where / extent / pose / wardrobe / action / camera as the question). Also check the cut: the first frame of each later segment shows its shot's keyframe composition (framing and place), and the cuts fall within 0.75 s of the brief's times. A segment that misses its block, a drifted or missing cut, or a continuity constraint broken = a failed review.
4. **Retry, then fall back.** A failed review: ONE re-render with a corrected prompt (`enhance_prompt` with the review text) and a new seed. A second failed review: NEVER a third bundle attempt. Call `clip_plan(storyboard)` and use the "Single-clip fallback for bundle" blocks of this bundle: re-shoot the shots as single clips with `shoot_clip` (sections 2-6; `clip` = the `clip_ref:` line of that member's fallback block, `<storyboard key>#<shot id>@<md5>`; the server binds its start frame and pictures, and the `picture_map` is `shoot_clip`'s own - pass the shot's lines from the member block as `context`; own prompt; mode `cut` - a bundle joins only cut junctions), one render per member block, then join them in order into the canonical `.mp4` (`assemble-scene` concat recipe: `ffmpeg -y -nostdin -f concat ...`). The task's render budget is two failed renders: if it is used up, `task_complete` stating the problem instead.
5. **Audit and finish.** `render_info` on the returned `renderId`: it is the bundle workflow and the prompt is yours behind the server's `Shot limits` block. Write `_prompt.txt` from the exact rendered prompt (`render_info`'s, the block included) (a fallback lists each single clip's prompt under a `[shot <id>]` heading). `task_complete`: 1-3 lines - mode `bundle`, measured duration, per-shot review result, and `fell back to single clips` when it did.
